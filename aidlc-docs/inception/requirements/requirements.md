## 2. プロダクト目標（Why）

- 「きく」ことを目的とした時間・取り組みを促進し、広く実践できるようにする（耳の育成）。
- 場所・経済状況に左右されず、誰もが継続的に「聴く力」を育める環境をスマホ/タブレットで提供。
- コア体験: **録音 → 加工 → 自身の音で「聴き分ける」オムニバス型ミニゲーム**。
- 位置づけ: 音楽教育の前段としての「音響教育」（「演奏」より「聴く」に重き。ウィレムスメソッド導入段階に着想）。

## 3. 対象ユーザー / プラットフォーム

- **対象ユーザー**: 音楽学習者全般、「聴く」ことに興味がある人、（資料により）子ども・音楽教育者。
- **プラットフォーム（Q1=C）**: iOS / Android 両方対応を最終目標とし、**MVP はどちらか片方から着手**（対象OS・最小バージョンは NFR/Construction で確定）。
- **画面の向き**: **縦・横の両対応**（ポートレート／ランドスケープ）。スマホ・タブレットの多様な画面サイズ・アスペクト比で破綻しないレイアウトとする（詳細は NFR-11/NFR-12）。
- **形態**: スマートフォン・タブレット向けアプリ。**サーバー無し・完全オフライン**（Q12=A）。

## 4. スコープ定義（MVP＝段階型 / Q2=A＋明確化Q1=A）

今回の計画スコープは **段階型 MVP**。基盤フェーズを完成させた後、続けて最初のゲームまでを本計画に含める。

### フェーズA：基盤（Foundation）
- 画面遷移の骨格（メイン→ホーム→各モジュール）
- 初回ユーザー登録（Q11=A＋明確化Q2=A：MVPに含める）
- Rec（録音・加工・保存）
- MySoundCollection（保存音の一覧・再生・管理）

### フェーズB：最初のプロトタイプゲーム
- ①音合わせ（Q3=A）
- ユーザーの保存音をゲーム出題に使用（Q8=A：リアルタイムでピッチ加工しバリエーション生成、加工音は非保存）
- weekly theme（お題表示→Rec導線）

### スコープ外／後続（今回のMVP計画に含めない）
- ③共有（Place）：**MVPでは無効化/非表示**（Q4=A。既存Placeシーンは導線から外す）
- ②音並べ以降のゲーム（②〜⑧）
- ゲーミフィケーション（経験値・カエルコイン・ライフ・課金）：**全除外**（Q9=A）
- ⑤テスト（能力変化計測）画面：研究会後に検討

## 5. 機能要件（Functional Requirements）

### 5.1 アプリ基盤・ナビゲーション
- **FR-01**: メイン画面→ホーム画面→各モジュール（Rec / Collection / ゲーム選択 / weekly theme）へ遷移できる。ホームに戻れる。
- **FR-02**: 既存の画面遷移の不具合（例: Place遷移文字列 "place" と `Place.unity` の大文字小文字不一致）を解消する。MVPでは Place への導線を無効化/非表示にする。

### 5.2 初回ユーザー登録
- **FR-03**: 初回起動時に簡易ユーザー登録（生まれた年・ニックネーム）を行い、端末ローカルに保存する（ユーザー識別用）。
- **FR-04**: 登録情報は編集可能。入力は妥当性検証を行う（年の範囲・ニックネーム長）。

### 5.3 Rec（録音・加工・保存）
- **FR-05**: マイクから録音できる。**録音時間は3秒固定**（Q5=A）。録音/停止/再生の操作を提供。
- **FR-06**: 録音音を加工できる。加工は再生時に反映し、保存時も加工後の状態で保存する。加工項目（企画準拠）:
  - リバーブ
  - ノイズリダクション（0/弱/中/強）
  - ピッチ調整
  - 音色エフェクト（**企画準拠：なし/ロボット/コーラス系** / Q7=A）
  - 各加工にバイパス（on/off）を設ける（操作性が悪い場合は省略可）
- **FR-07**: 録音・加工の実装を **`VoiceRecordingSection`（Unity標準AudioFilter）に一本化**（Q6=A）。重複する `RecorderWithEffects` は整理・統合する。
- **FR-08**: 加工済み音を **WAVE（16bit PCM）** で保存する。保存時に加工設定（`SoundEffectSettings`）も対で保存する。

### 5.4 MySoundCollection（コレクション）
- **FR-09**: 保存音を一覧表示し、視聴・削除できる。
- **FR-10**: メタデータを企画通り拡張する（Q10=A）：日付、タイトル（デフォルトは日付）、写真（任意）、メモ（任意）、ニックネーム。
- **FR-11**: 月別絞り込み・キーワード検索を提供する。
- **FR-12**: 保存音・設定・メタデータは端末ローカルに保存する（`Application.persistentDataPath` 配下）。

### 5.5 weekly theme（お題）
- **FR-13**: 週替わりの「音のお題」を表示する。現状のオノマトペ表示に加え、**お題タップから Rec へ遷移**できるようにする。
- **FR-14**: お題テキストは企画（Sさん）側が用意する内容に差し替え可能な構成にする。

### 5.6 ミニゲーム ①音合わせ
- **FR-15**: お手本音（カエル）と複数の選択肢音（おたまじゃくし）を提示し、タップで音を確認、ドラッグで解答できる。
- **FR-16**: 音色・音高・強弱の聞き分けを扱う（音の長さの扱いは研究会で確定）。
- **FR-17**: 正解時に演出（おたまじゃくし→カエルへ進化）を行う。
- **FR-18**: 共通パラメータ（出題数、選択肢数、難易度）を設定可能にする。難易度はピッチ間隔（セント）で表現（かんたん/ふつう/むずかしい/とても難しい）。
- **FR-19**: **ユーザーの保存音を出題素材に使用**し、リアルタイムでピッチ加工したバリエーション（例: オリジナル/±10/±20セント）を生成して出題する。生成した加工音は保存しない（Q8=A）。

## 6. 非機能要件（Non-Functional Requirements）

- **NFR-01（プラットフォーム）**: iOS/Android 両対応を目標。MVPは片方から。**画面の向きは縦・横の両対応**。最小OS・詳細解像度方針は NFR/Construction で確定。
- **NFR-02（オフライン/ローカル）**: サーバー・外部通信なしで全機能が動作する。データは端末ローカルのみ（Q12=A）。
- **NFR-03（音声仕様）**: 録音3秒固定、保存は WAVE 16bit PCM。ゲーム出題のピッチ加工はリアルタイム処理（保存しない）。
- **NFR-04（プライバシー）**: 子どもの利用を想定。個人情報（生年・ニックネーム・写真・メモ）は端末外に送信しない。ログに個人情報を出力しない。
- **NFR-05（ユーザビリティ）**: 初心者（企画者S）・子どもが扱える簡潔なUI。視覚に頼らず音中心でも成立する操作性。UIモチーフはカエル/おたまじゃくし/蓮。
- **NFR-06（パフォーマンス）**: 録音・再生・リアルタイム加工が体感遅延なく動作する。ゲーム出題のピッチ加工はモバイル端末で実用的な処理時間に収める。
- **NFR-07（データ堅牢性 / Resiliency R1=A）**: ローカルデータの破損防止を重視（保存の原子性、破損ファイルの安全な読み飛ばし、空/欠損時のフォールバック）。クラウドDRは対象外。
- **NFR-08（保守性）**: 録音実装の一本化、`Scean.cs` 等の不要コード整理、Assembly Definition 整備、テスト整備を行う。
- **NFR-09（テスト容易性 / PBT Q15=A）**: WAVエンコード/デコード、cents↔pitch変換、設定JSONのシリアライズ等はプロパティベーステスト（ラウンドトリップ/不変条件）を導入する。
- **NFR-10（変更管理 / Resiliency R2=A）**: Git ブランチ運用＋PRレビュー＋変更メモ＋ロールバック手順の軽量プロセスを採用する。
- **NFR-11（レスポンシブUI）**: 様々な画面サイズ・解像度・アスペクト比（スマホ〜タブレット、主要比 19.5:9〜4:3 等）で表示が破綻しないこと。全 Canvas で CanvasScaler = Scale With Screen Size を用い、**縦・横 両対応**に耐える参照解像度・Match 方針を統一する（現状は参照 1920×1080・Match 0.5 で横基準のため、両対応向けに再設定）。レイアウトは Anchor／レイアウトグループで構成し、固定ピクセル依存（例: `ScrollRectSnapLoop` の `itemWidth 850px`）を相対指定へ見直す。向き変更（オートローテーション）時にレイアウトが再構成され操作要素が見切れない。
- **NFR-12（Safe Area 確保）**: ノッチ／パンチホール／ホームインジケータ／角丸を避け、`Screen.safeArea` に追従する SafeArea コンポーネントを各画面のルートに適用する。縦・横いずれの向きでも操作要素がシステムUIに隠れないこと。`ProjectSettings` の `androidRenderOutsideSafeArea`（現在 1）と整合させる（現状 SafeArea 対応スクリプトが未実装のため新設）。

## 7. 前提・制約

- 研究会（今月開催予定）後に、各ゲームの出題数・音域・微分音の扱い・難易度設計等の細部が調整・確定される（本要件は暫定、更新前提）。
- 助成金・公募スケジュール（実施期間 2026-07〜2027-03、中間報告11月、ART DX EXPO 2027-03）に整合させる。
- Sさん=企画・画面・音素材、前本=実装・技術設計、の分担。
- **画面の向きは縦・横 両対応に決定**（2026-07-15 ユーザー指示）。既存の CanvasScaler 参照解像度（横基準 1920×1080）とオートローテーション設定は、両対応向けに設計段階で再調整する。
- **開発規約**: Unity のシーン／GameObject／プレハブ操作は Unity 標準 MCP サーバー（unityMCP）経由で行う（詳細は `../reverse-engineering/technology-stack.md`）。
